# Kokkos CUDA: `cudaErrorInvalidDeviceFunction` in `-O2` builds when a file only destroys an object

> This reproducer, its build scripts and this README were generated by
> [Claude Code](https://claude.com/claude-code), Anthropic's AI coding assistant, including the
> investigation behind the description of the cause.

A minimal reproducer for a Kokkos CUDA program that runs at `-O0` and `-O1` but aborts at `-O2` and
`-O3`:

```
terminate called after throwing an instance of 'std::runtime_error'
  what():  cudaFuncGetAttributes(&attr, func) error( cudaErrorInvalidDeviceFunction): invalid device function
  .../kokkos/install/include/Cuda/Kokkos_Cuda_KernelLaunch.hpp:140
```

## Summary

- **Issue.** A kernel launched from a virtual member function of a class template fails at `-O2` with
  `cudaErrorInvalidDeviceFunction` when another translation unit only destroys an object of that
  class. The kernel never starts.
- **Cause.** Kokkos declares its CUDA kernels `static` (`cuda_parallel_launch_local_memory`,
  `Kokkos_Cuda_KernelLaunch.hpp:85`), so each translation unit has its own host stub, which must be
  registered with the CUDA runtime. The file that only destroys the object compiles a host stub for
  the kernel but no device code, so that stub is never registered. At `-O2`, GCC places that
  unregistered stub inside the COMDAT group of the shared Kokkos launch code, and the linker keeps
  that copy. The launch then asks CUDA about a stub it has never seen.
- **Fix.** Compile the code that launches the kernel as one translation unit, for example as a CMake
  unity build (`-DCMAKE_UNITY_BUILD=ON -DCMAKE_UNITY_BUILD_BATCH_SIZE=0`). This is verified in the
  reproducer and in the application where the bug was found. The underlying defect is in how Kokkos
  declares its kernels; see [Fix](#fix) for the options.

## Background

The bug was found in [Comet](https://github.com/ComputationalGasDynamicsLab/Comet), a Kokkos-based DSMC
particle code that stores particles in a [pumi-pic](https://github.com/SCOREC/pumi-pic) `DPS`
structure. Comet's Debug build ran, but every `-O2` or `-O3` build aborted at the first particle
move, in the kernel launched by `pumipic::DPS<...>::rebuild()`. This repository reduces that
failure to plain Kokkos.

## Reproducing

```bash
cd minimal_kokkos_only
export KOKKOS_ROOT=<Kokkos install prefix>          # contains lib64/cmake/Kokkos
export NVCC_WRAPPER=<Kokkos source>/bin/nvcc_wrapper
export CUDA_ROOT=<CUDA toolkit>                      # e.g. /usr/local/cuda-12.5
./run_all.sh
```

`run_all.sh` builds and runs five configurations, each in `build_<tag>/`. The output on the system
where it was tested:

```
O0         exit=0     PASS: v(0) = 1, expected 1
O1         exit=0     PASS: v(0) = 1, expected 1
O2         exit=134   what():  cudaFuncGetAttributes(&attr, func) error( cudaErrorInvalidDeviceFunction): invalid device function
O3         exit=134   what():  cudaFuncGetAttributes(&attr, func) error( cudaErrorInvalidDeviceFunction): invalid device function
O2_unity   exit=0     PASS: v(0) = 1, expected 1
```

`O3` is `-O3 -DNDEBUG`; `O2_unity` is `-O2` built as a unity build.

`build.sh` builds without running: `./build.sh` with no arguments builds all five configurations,
and `./build.sh <tag> "<flags>" [cmake options]` builds one, for example
`./build.sh O2 "-O2" && ./build_O2/repro`.

**Tested toolchain:** GCC 11.5.0 as the host compiler through `nvcc_wrapper`, CUDA 12.5 without
relocatable device code, Kokkos 4.6.02 built as shared libraries with `Kokkos_ARCH_ADA89=ON`,
`Kokkos_ENABLE_CUDA_LAMBDA=ON` and `Kokkos_ENABLE_DEBUG=ON`, on an RTX 4060 (sm_89). Other compiler,
CUDA and Kokkos versions have not been tested.

## The code

| File | Role |
|---|---|
| `structure.hpp` | a class template `Structure<T>` with a virtual `rebuild()` that launches a `KOKKOS_LAMBDA` kernel, and a user-provided destructor defined outside the class body that frees a heap member |
| `destroy.cpp` | only `delete`s a `Structure<double>`; never constructs one and never calls `rebuild()` |
| `make.cpp` | constructs a `Structure<double>` |
| `main.cpp` | constructs through `make()`, calls `rebuild()` through a base-class pointer, checks the result, destroys through `destroy_only()` |

`destroy.cpp` is listed first in `CMakeLists.txt`, so the linker keeps its copies of shared (COMDAT)
code. `Structure<T>` has the shape of pumi-pic's `DPS<...>`: `rebuild()` is virtual, and the
destructor is `DPS<...>::~DPS() { delete aosoa_; }`.

## Cause

Each step below was observed in the reproducer's object files and binaries.

### 1. A host stub without device code

`destroy.cpp` never calls `rebuild()`. Its destructor still makes GCC emit `Structure<double>`'s
vtable, and emitting the vtable instantiates every virtual function, so `rebuild()` and the host
stub of its kernel are compiled into `destroy.cpp.o`. nvcc's device pass does not instantiate
`rebuild()` in this file, so the object holds the host stub but no device code, and its static
constructor never registers the stub with `__cudaRegisterFunction`.

| Object (`-O2`) | `rebuild` kernel host stubs | `rebuild` in the embedded device code |
|---|---|---|
| `destroy.cpp.o` | 1 | none |
| `make.cpp.o` | 1 | present |
| `main.cpp.o` | 0 | none |

The same asymmetry was found in Comet's two source files that delete a `DPS` without constructing
one.

### 2. Shared launch code that points at private stubs

Kokkos declares the kernel `static`:

```cpp
template <class DriverType>
__global__ static void cuda_parallel_launch_local_memory(const DriverType driver)
```

so every translation unit that instantiates it has its own private host stub. The code that takes
the stub's address and asks CUDA about it (`Kokkos::Impl::ParallelFor<...>` and
`get_cuda_kernel_func_attributes<...>`) is a class template, emitted into a COMDAT group in each
translation unit, of which the linker keeps one copy for the whole program. Each copy refers to a
different translation unit's stub. This breaks the One Definition Rule, which requires no
diagnostic.

### 3. At `-O2`, GCC moves the unregistered stub into the COMDAT group

In `destroy.cpp.o` nothing but the `ParallelFor` code refers to the stub, since no registration code
does. At `-O2` GCC places the stub in the COMDAT group of that `ParallelFor` code:

| `destroy.cpp.o` | local kernel stubs | stubs inside a COMDAT group |
|---|---|---|
| `-O1` | 1 | 0 |
| `-O2` | 2 | 1 |

At `-O1` the `rebuild` stub in `destroy.cpp.o` is optimised away entirely, and the copy that runs is
`make.cpp`'s.

### 4. The linker keeps the copy with the unregistered stub

In the linked `-O2` binary:

| `rebuild` kernel stub | registered with CUDA | used by |
|---|---|---|
| from `destroy.cpp.o`, inside the COMDAT group | **no** | the kept `ParallelFor` code |
| from `make.cpp.o` | yes | nothing |

The backtrace at the throw is:

```
main
 -> Structure<double>::rebuild
 -> Kokkos::parallel_for
 -> Kokkos::Impl::ParallelFor<...>                 (the copy kept from destroy.cpp.o)
 -> Kokkos::Impl::get_cuda_kernel_func_attributes
 -> cudaFuncGetAttributes(<unregistered stub>)     -> cudaErrorInvalidDeviceFunction
```

### What the failure needs

Found while reducing the reproducer:

- **Needed:** a translation unit that only destroys the object (without one, every file with the
  host stub also has its device code, and the program passes); that file must not call `rebuild()`
  (a call makes nvcc generate and register the device code there); a user-provided destructor
  defined outside the class body (with the implicit destructor, GCC at `-O1` and `-O2` no longer
  emits the vtable in `destroy.cpp`).
- **Not needed:** defining `rebuild()` outside the class body (an in-class definition fails the same
  way); pumi-pic, Cabana or MPI.

## Fix

| Option | Status |
|---|---|
| **Unity build:** compile all sources that launch the kernel as one translation unit (`-DCMAKE_UNITY_BUILD=ON -DCMAKE_UNITY_BUILD_BATCH_SIZE=0`). There is then a single stub, registered by the object that launches it. | **Verified.** Passes in the reproducer at `-O2`. In Comet, an `-O3 -DNDEBUG` unity build runs, and its results match the Debug build within run-to-run noise. |
| **Host optimisation `-O1`.** | Works in the reproducer and in Comet, but only because GCC happens to lay the code out differently; it does not remove the defect. |
| **Upstream (Kokkos):** do not give the kernel internal linkage (drop `static` from `cuda_parallel_launch_local_memory` and its constant- and global-memory variants), so that all translation units share one stub. | Proposed, not tested. |
| **Relocatable device code** (`Kokkos_ENABLE_CUDA_RELOCATABLE_DEVICE_CODE=ON`), which changes how kernels are registered. | Not tested. |
| **Application side:** avoid translation units that destroy such an object without also instantiating its kernels, or explicitly instantiate the class template in one file and declare it `extern template` elsewhere. | Not tested. |

Compiler flags do **not** fix it. Tested in Comet at `-O2`/`-O3`:

- disabling identical-code folding (`-fno-ipa-icf`), or every `-fno-ipa-*` optimisation, still
  leaves unregistered kernels;
- disabling identical-code folding together with the four `-O2` inlining flags
  (`-fno-inline-functions -fno-inline-small-functions -fno-partial-inlining -fno-indirect-inlining`)
  leaves no unregistered kernels, but exposes a second crash of the same kind: a call through a null
  function pointer held by nvcc's per-translation-unit extended-lambda helper `__nv_hdl_helper`.
